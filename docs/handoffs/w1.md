## What shipped (https://github.com/AmritusG/DXVKit-Plus, PUBLIC, tag v0.1.0)
- dxvkit-plus-core (#![forbid(unsafe_code)], no GPU dependency): QuickTime/MP4 demux with the tmcd timecode track; HAP decode for every variant in the Vidvox spec (Hap1, Hap5, HapY, HapM, HapA, Hap7/HAP R, HapH BC6U/BC6S) with Snappy and chunked Decode Instructions (parallel); CPU BC1/BC3/BC4 and a new BC7 decoder written from the Khronos spec (CPU RGBA on request); frame cache with read-ahead; exact-time transport (loop, bounce, once, random; reverse; any speed; frame-exact seek, step, scrub, cues; beat and timecode sync); the platform Backend trait plus a documented Windows (Media Foundation + DX12) stub. DXV tracks are probed, not decoded.
- dxvkit-plus-wgpu (wgpu 30): create_bc_texture/write_bc, WGSL conversion (HAP Q YCoCg, alpha-only, HDR, 4:2:0 BT.601/709/2020), read-back.
- dxvkit-plus-apple (the only crate with unsafe; 43 unsafe sites, 43 SAFETY comments): AVFoundation/VideoToolbox decode (H.264, HEVC, ProRes 422/4444, MJPEG), frame-exact, zero-copy into wgpu Metal through two routes: CVMetalTextureCache (default) and direct IOSurface.
- dxvkit-plus CLI: probe, decode (frame N to PNG, GPU or --cpu), bench, verify, gen-pattern.
- Docs: README (codec table, quick start as a compiled example, CLI, Mac Studio benchmarks, roadmap, the not-affiliated line), docs/ARCHITECTURE.md (with the import-route measurements and the C-ABI mapping), docs/PROVENANCE.md, ATTRIBUTION.md, CONTRIBUTING.md, CHANGELOG.md, LICENSE (MIT, Amrit Rosell), deny.toml, scripts/mint-{fixtures,bench}.sh, scripts/bench-all.sh.
- Fixtures: 14 CC0 files (628 KB, no LFS): 12 tiles_* from Loombda-rs (cp -p, unchanged) and 2 synthetic files (Hap7 random BC7 blocks of all 8 modes; HapH solid BC6H). Every one has a sidecar with its SHA-256, checked by a test.
- C-ABI readiness (for W2): every fieldless public enum is #[repr(u32)] with explicit values, and MediaError::code() gives stable numbers. Both are pinned by core/tests/abi.rs, and ARCHITECTURE maps every public type to C.
- LGPL warning recorded (PROVENANCE, CONTRIBUTING, README roadmap): a future HAP Q encoder must never derive from hap-qt-codec's YCoCg encoder (LGPL-2.1, Id Software). Write it from van Waveren & Castaño (2007) instead.

## Measured (Mac Studio Mac16,9, M4 Max, 36 GB, macOS 26.6.2)
- HAP vs our source pattern: Hap1, Hap1×4 chunks, Hap5 and HapA max 0/255. HapY, HapM and HapM×4 max 2/255 (mean 0.35), within the brief's tolerances.
- GPU vs CPU on every HAP fixture frame: ≤ 1/255 (HAP Q needed an exact-palette CPU oracle: integer truncation gave 2). BC7 CPU decoder vs the GPU: bit-exact on 524,288 px of random blocks in all 8 modes. Hap7 fixture: CPU == GPU, 0 diff.
- Native: H.264, HEVC, ProRes 422, ProRes 4444 and MJPEG are 24/24 frames zero-copy each. Copies: 0, blits: 0, bytes uploaded: 0 per frame. The only GPU work is the conversion pass. Shuffled seeks are identical to sequential decode on every frame. ProRes 4444 zero-copy BGRA is bit-exact with Apple's CPU read-back. Our 4:2:0 conversion matches Apple's in tile interiors (mean 0.38–0.77/255), and whole frames are closer to the source than Apple's own conversion (H.264 14.00 vs 14.98).
- Fuzz: 600 s, 8 threads, 624,398,124 execs, 0 crashes, 0 hangs (demux + HAP + BC7 CPU path).
- Decode p50 (ms): Hap1 1080p 0.58, 4K 2.36 (0.69 with 8 chunks); HAP Q 1080p 0.90, 4K 3.38; HapM 4K 3.95. End to end, 4K Hap1 with 8 chunks: 1.99. 16 layers of Hap1 1080p decode in 1.66 ms total (about 0.10 ms per layer); 16 layers decode + upload + convert in 6.1 ms p50. Import route mean p50: cache 1.21 ms vs IOSurface 1.43 ms (p99 8.3 vs 8.5), so the cache route is the default. Full tables are in the README; raw data in docs/data/.
- Gates: fmt clean; clippy -D warnings clean; nextest 60/60 (GPU required); cargo-deny bans/licenses/sources ok.

## Deviations (and why)
1. No LMBD: Amrit's decision after I found no LMBD code anywhere (Loombda, Loombda-rs, transcripts). So there is no dxvkit-plus-lmbd-enc, no encode-lmbd, no docs/LMBD.md and none of the LMBD tests (BUILD+TEST 5).
2. No DXV decode: P1-1 still hasn't landed on Loombda-rs origin/main (d2c0c43), so per the brief DXV moves to W2. The 334-vector check and DXV fuzzing move with it; the fuzz run covered demux, HAP and BC7 instead.
3. The GitHub description and tagline name DXV and LMBD as the brief specified. The README says plainly that both are roadmap items, not in 0.1.0.
4. Native layout: 4:2:0 is requested only for H.264 and HEVC, and BGRA for everything else. Measured: ProRes 422 forced through 4:2:0 lands 13.4 mean error from the source, vs 10.8 as BGRA.
5. Synthetic Hap7 and HapH fixtures, because no encoder we may use writes them. Re-minting with scripts/mint-fixtures.sh reproduces all 7 HAP fixtures byte for byte. The 5 native fixtures differ in bytes (Apple's encoders) but pass verify.
6. deny.toml has one crate-scoped exception: unicode-ident (Unicode-3.0, permissive), via serde's derive macros.
7. Native-decode p99s (12–50 ms) include reader restarts (each new pass is a seek), and the GPU p99s (about 10 ms) include clock ramp-up. The p50s are the steady state.
8. The fuzzer ran before a one-line lint fix to how it builds one seed (the seed bytes are identical).
