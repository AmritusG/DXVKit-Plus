# W9 — EXPLORE: BC7 tiles (A) and adaptive tile sizes (B) in LMBX

## Answer in one line
BC7 tiles only help the synthetic detail card. At LMB7's bytes it goes from 20.99 to 27.38 dB at 960×540, and from 20.28 to 22.57 dB in the 1080p eye clip, where LMB7 is 21.85. On real footage they give nothing or lose a little. **Recommendation: do not ship A now; drop B1; prototype B2 (16/32 DCT) next.**

CHECKPOINT, not COMPLETE, for two reasons:
- B was bounded on paper, not built as a prototype.
- The GPU speed numbers are not valid as absolute numbers: Arena, Blender and another job shared the GPU (Metal System Trace below). v3 and v4 are within noise of each other.

## What was built (branch w9-explore, prototype only)
- **Bitstream:** prototype LMBX v4 = v3 plus tile colour mode 4 (BC7). The tile's stream 0 holds 64 BC7 blocks, raster over the tile's 8×8 grid of 4×4 blocks. v1, v2 and v3 parse and decode unchanged; the 0.7.0 vectors and tests pass.
- **Encoder:** the BC7 tile is a per-tile candidate next to DCT, palette and quad.
  - Blocks come from our bc7enc_rdo port: λ, uber, partitions.
  - Cost = 8 × zstd(block bytes) × a multiplier.
  - The colour guard applies, as for every candidate.
  - CLI flags: `--bc7-tiles L --bc7-mult X --bc7-parts N`.
- **A3, WGSL BC7 decoder:** in `expand_block`.
- **A4, hardware route:**
  1. A scatter kernel writes the blocks into a staging area in the table buffer.
  2. `copy_buffer_to_texture` copies them into a `Bc7RgbaUnorm` texture.
  3. `textureLoad` + `pack4x8unorm` reads them in the expand pass.
- **GPU vs CPU:** both routes are bit-exact with the CPU decoder on this Mac, per the new test `lmbx_v4_bc7_tiles_gpu_decode_is_bit_exact_with_the_cpu` (36 hostile frames, 191 BC7 tiles, both routes).
- **Is route 2 bit-exact in general?** The BC7 decode is fully specified (integer interpolation), and Apple's hardware matched our CPU reference on every tile tested. That is verified here, not guaranteed on other GPUs, so route 1 stays as the portable fallback.
- **How route 2 composes with the RGBA output:** the texel goes through the same expand path as direct tiles, so alpha and the 4:2:2 halo are unaffected.
- **Lab:** `examples/w9_lab.rs` covers the per-tile diagnosis, the oracle, BC7 timing, the merge bound and the transform-size estimate. `lmbx_quality` gained BC7 arms.

## B — adaptive tile sizes (bounded, not built)
- **B1 (quadtree split/merge):**
  - The most it can save is the signalling. That is 45–53% of stored bytes on graphics, but graphics is already lossless at ≤ LMB7.
  - On natural content signalling is only 3.4–6%, so merge saves ≤ 2.5–4.5%, about 0.1–0.3 dB.
  - Splitting below 16×16 is what quad tiles already do, and they are rarely chosen on natural content.
  - **Drop.**
- **B2 (DCT 8/16/32)**, estimated from the luma float DCT and empirical entropy (`bsize.txt`). Gain at equal bits:

  | content | gain |
  |---|---|
  | real detail | +1.3 to +1.8 dB |
  | glow | +0.3 to +0.7 dB |
  | grain | +0.1 dB |

  The estimate is optimistic: float transform, luma only, no signalling. It needs an integer 16/32 prototype with GPU IDCT before any claim. **Worth a W10.**
- **B3 (RD search):** not built. It follows B2.
- **C (combined):** equals best A, since there is no B to combine.

## Deviations
- B1–B3 bounded or estimated, not prototyped.
- GPU speed measured on a shared GPU, so the numbers are noisy.
- The eye LMBX 0.7.0 arm was encoded by the w9 binary without BC7. The v3 path is unchanged; the 0.7.0 tests pass.
- Refusal test: its "future version" moved from 4 to 5, because the prototype parses 4.
- Eye detail = one frame held for 60 frames, as the card is a still.
