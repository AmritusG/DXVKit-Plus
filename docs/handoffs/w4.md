# DXVKit Plus W4 — DXV decode, v0.4.0

## What shipped
- v0.4.0 (tag pushed), commit fd9dd4d. DXV decodes in `dxvkit-plus-core::dxv`, ported from Loombda-rs's
  safe-Rust port of DXVKit 1.0.0. It is wired into `source` (`DxvSource`, fixed layout so staging and
  decode_into work), wgpu, the CLI, the fuzzer and the docs. The GitHub description now names DXV and
  keeps the not-affiliated line.
- Alpha: `AlphaMode::{Straight (default), Premultiplied}` = `ImportOptions::alpha_mode`, CLI
  `--alpha-mode`. Premultiplied un-premultiplies on output, `min(255, round(c*255/a))`, with the same
  integer arithmetic on CPU and GPU.
- New: `Shading::DxvYcocg { alpha, premultiplied }`, `Shading::RgbaPremultiplied`, `MediaError::Dxv`
  (code 12), `dxv::Variant` repr(u32) 0..5, `bc::unpremul`. ABI values are pinned in `core/tests/abi.rs`
  and mapped in ARCHITECTURE.
- GPU: DXV High Quality uploads its BC4/BC5 blocks as integer texels (Rg32Uint/Rgba32Uint). A separate
  WGSL pass (`DXV_HQ_WGSL`) decodes the exact palettes and spec 8.4 folding in integers. DXT1/DXT5
  upload as BC textures and qualify for direct_view.
- Bug found and fixed: `planes_to_rgba` indexed blocks by display width, but DXV planes are coded to
  16 wide. It now uses the plane's own width.

## DIAGNOSE extraction (Loombda-rs @ 9ec3dea, at or after f57d1da; DXVKit @ 36209e0)
- Variants handled: DXV3 DXT1 (BC1), DXT5 (BC3), YCG6 (Y BC4 + CoCg BC5 at half size), YG10 (Y+A BC5 +
  CoCg BC5). Stored payloads (flag 1). Legacy DXDI DXV1/2: LZF or stored, DXT1/DXT5 from type bit 0x40.
  The packet decides the variant, never the FourCC (spec 2.2); DXD3, DXD4 and DXDI all route to it.
  HQ opcode streams can be stored, fill or FSE; the two sections decode on two threads.
- Alpha handling in the port: the decoder never premultiplies. `blocks_to_rgba(premultiply)` is
  DXVKit's straight-to-premultiplied option, used only for the C-core differential. Loombda's per-clip
  `alpha` was straight / premultiplied / opaque; DXVKit Plus exposes Straight / Premultiplied (Amrit's
  ruling, "Straight").
- Files ported and their licences: `dxv/{mod,blockcopy,hq,lzf,rgba}.rs`, copied with cp -p from
  Loombda-rs `crates/loombda-media/src/dxv/` @ 6795193 (Amrit's own code; Loombda-rs is
  LicenseRef-Proprietary, Amrit's, released here under MIT). That code ports DXVKit's packet.c,
  blockcopy.c, legacy.c, hq.c and pixels.c (MIT, Amrit's, clean room from its own DXV_FORMAT.md). Also
  added `bytes::{copy_within, put}` (same source).
- Vectors: 334 rows in total. Committed is the same MIT subset Loombda commits: glenc + synthetic +
  invalid, 74 rows, 34 files, 252 KB, synthetic content only, copied from DXVKit itself and
  byte-identical to Loombda's. The resolume group, anything derived from it, and the arena forms
  (DXVKit-encoded ffmpeg testsrc2) are not committed. The full run uses `DXVKIT_DIR=<checkout>`;
  `DXVTOOL=<built dxvtool>` adds the live C-core differential. Four CC0 DXV tile fixtures come from
  Loombda (minted with dxvtool encode).
- Decisions D8, D9, D10 (Loombda): D8 is this port; D9 means fixtures re-minted from our own footage
  (we take only those plus the MIT vectors); D10 means no FFmpeg anywhere — ffmpeg was used here only
  as an external oracle for P1-1.

## Deviations
1. GPU vs CPU for DXT1/DXT5 is ≤ 2/255, not 0. That is the GPU's fixed-function BC1/BC3 against
   DXVKit's truncating integer convention, which DXVKit spec 8.1 records for Arena's GPU too. I kept
   hardware BC so direct_view keeps working. HQ was made exact instead (that needed its own integer
   pipeline).
2. Breaking API for 0.4.0: two new `Shading` variants and the `ImportOptions::alpha_mode` field
   (struct literals need `..Default::default()`).
3. The P1-1 card was regenerated, not reused: Loombda's card was never committed. Its numbers differ
   slightly from the spike's but tell the same story.
4. The bench clips are GlEnc DXV (large, no FSE), not Alley output, and are not committed.
