## Diagnose (read, then measured before changing code)
- wgpu 30 source. `Queue::write_texture` (wgpu-core `queue.rs`) calls `StagingBuffer::new` on every call. That makes a fresh `MAP_WRITE|COPY_SRC` buffer, which the Metal backend creates with `newBufferWithLength` (shared storage, write-combined). wgpu then memcpys the bytes in and records a blit into the internal PendingWrites command buffer. Textures are always `Private`.
  - `StagingBelt` reuses mapped chunks and remaps them on recall.
  - Mapped write memory is exposed only as `WriteOnly<[u8]>` (gfx-rs/wgpu#8897, write-combining), never `&mut [u8]`.
  - On the M4 Max adapter: `TIMESTAMP_QUERY` yes, `INSIDE_ENCODERS` and `INSIDE_PASSES` no. So wgpu timestamps can only bracket passes, and the blit's GPU time comes from xctrace.
- Apple docs, read from the doc JSON:
  - `makeTexture(descriptor:offset:bytesPerRow:)` linear textures accept only ordinary or packed colour formats, never compressed ones. Zero-copy BC7 is ruled out.
  - `replaceRegion` "runs on the CPU and immediately copies".
  - Shared is the default storage on Apple silicon. BC formats never get lossless compression.
  - Apple does not document what xctrace's channel intervals mean. A developer-forums thread says blit placement varies, and ours show up on "Compute". I treated an interval as GPU execution of that encoder and cross-checked against the microbenchmarks.
- Before breakdown, 16 × 1080p, p50 ms. CPU buckets are wall clocks from the new bench; GPU is the Metal System Trace union of our intervals over 20 steps.

| Clip | Step | CPU decode | `write_texture` | Encode | Submit | GPU wait | GPU work/step (blit + convert) |
|---|---|---|---|---|---|---|---|
| LMB7 λ1 c8 | 10.0 | 4.28 | 4.16 | 0.46 | 0.33 | 0.82 | 1.68 (1.16 + ~0.5) |
| Hap1 c8 | 6.27 | 2.25 | 2.33 | 0.39 | 0.31 | 1.06 | 1.22 |
| HAP Q c1 | 21.7 | 6.43 | 5.97 | 0.67 | 0.39 | 4.32 | 1.42 |

- Biggest bucket: CPU decode, 43% of the LMB7 step. That is out of scope (W2b work). Next is `write_texture` at 42%.
  - Microbenchmark, 16 × 2 MB: `write_texture` takes 3.45 ms. A fresh buffer plus memcpy takes 3.42 ms; a persistent mapped buffer takes 0.62 ms. So **about 2.8 ms of it is wgpu allocating a staging buffer per call**.
  - The GPU was idle most of each step.

## What shipped (v0.3.0, additions only)
- **Persistent staging** (`FrameRenderer::upload_staged`, StagingBelt plus `copy_buffer_to_texture`). `render` is split into `upload` and `encode_convert`, which takes optional pass timestamps.
- **Pipelining.** `Uploader` keeps at most 2 submissions in flight and waits on a submission index, never `wait_idle`. The bench decodes ahead on per-layer threads.
- **Decode into staging.**
  - core: `FrameSource::layout` and `decode_into(&mut dyn PlaneSink)`. LMBD streams chunk by chunk through a reused buffer; the default decodes and writes whole planes.
  - wgpu: `Uploader::stage` gives a `StagedFrame` (`Send`, a `PlaneSink`), recorded by `FrameRenderer::upload_from_stage`.
  - `submit` refuses while a staged frame is open, because unmapping under a live view would panic inside wgpu.
- **Optional convert.** `FrameRenderer::direct_view` returns a `DirectView` for LMB7, Hap7, Hap5, and Hap1 (with `opaque`). Sampling it equals the conversion output exactly.
- `GpuError::code()`, pinned in `wgpu/tests/abi.rs`. The ARCHITECTURE C mapping is updated: `PlaneSink` stays Rust-side, and C passes a `StagedFrame` handle, not a callback.
- Bench: `--layers-only`, `--variants`, per-bucket breakdown, sustained fps, and decode→texture latency.
- `verify` checks the staged, decode_into and direct paths against `render` on every frame.
- The fuzz LMBD target now runs `decode_frame_into` too.
- Docs: README (intro, new upload-path quick start, "Getting frames onto the GPU (0.3.0)"), ARCHITECTURE ("Upload paths (0.3.0)", crates row, C mapping), CHANGELOG 0.3.0.

## Deviations
1. **Resolume Arena was running throughout and held 66–95% of the GPU** (Metal System Trace). The other session's Loombda-rs `m3_exit` tests added up to 16%, at load average 6–9.
   - Every GPU-side number is on a shared GPU. W2b's 16 ms step was probably affected too: the same v0.2.1 binary measured 7.5 ms today.
   - Comparisons are interleaved like-for-like. I did not quit Arena; it is Amrit's app.
2. The HAP Q 1080p plasma clip shows CPU vs GPU 2/255, and `verify`'s HAP tolerance is 1, so `verify` fails that clip.
   - It is pre-existing: the v0.2.1 binary gives the identical result.
   - It is within the brief's "HAP Q 2/255" tolerance, and the new paths equal the render exactly.
   - I did not loosen `verify`.
3. Shared-storage BC7 was measured and rejected, not built. `replaceRegion` costs 1.78 ms of CPU vs 0.54 ms for the staging memcpy (16 frames), to save a 0.3 ms GPU blit, and it can't take decode-into. No unsafe was added.
4. "Decode straight into GPU-visible memory" is a chunked copy, not in-place decode. wgpu only allows write-only access to mapped memory, and LZ decoders read back their output. LMBD chunks decompress into a cache-sized buffer and stream out. HAP uses the default (decode, then write).
5. Both throughput-optimal (decode-ahead) and latency-optimal (decode-into) paths ship. They measure better on different axes and serve different callers (cache-fed vs decode-on-demand), so neither is dead code.
6. Under xctrace, launches from a cwd under `~/Documents` stalled in dyld `getCWD` (a privacy check). Traces were launched from a scratchpad copy of the binary.
7. HAP Q pipelined latency (about 11 ms in into mode) is higher than v0.2.1's 7–8.6 ms step, in exchange for 2× throughput. Staged step mode is lower than v0.2.1 everywhere.
